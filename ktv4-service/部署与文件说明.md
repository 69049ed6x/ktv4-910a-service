# 四卡服务：部署与每个文件的说明

## 交付内容和验证范围

源码从当前运行服务器 `qiusy@218.25.40.86:/mnt/nvme0n1/ktv4` 下载。原始导出包含 10,141 个文件，每个原始文件的服务器绝对地址、大小和 SHA-256 在 `export_manifest.json` 中。包含服务本体、修改后的 vLLM、与实际安装一致的 vLLM-Ascend Python 文件、C++/AscendC 自定义算子及仓库内第三方构建源码。

不包含模型权重、驱动、CANN/ATB 安装包、Python 环境、依赖 wheel、已编译共享库、旧运行日志或编译缓存。仓库中第三方源码和生成的算子描述文件是构建上下文，不能当成可直接运行的二进制依赖。

新增 `setup.sh`、`deploy/` 和配置文件加载功能，方便换目录和安装。推理数学、CPU 专家、权重加载、采样实现保持原导出版本。`config/portability_changes.json` 列出迁移修改，`delivery_manifest.json` 逐文件记录本包校验值和原机来源。

原服务器已经完成实际四卡冷启动、中文问答、算术、多轮问答、重复启动验收。迁移入口另在原服务器隔离目录中检查安装计划、服务/API 导入、CPU INT8 算子、NPU 数量、原生库 ABI、分片完整性和 tokenizer，具体结果在 `config/portable_validation.json`。这不等于在另一台服务器完成了全新依赖安装和全量原生重编译；目标机器仍需按下面的步骤完成真实问答验收。

## 目标机器要准备的环境

**只有驱动和权重不足以运行。** CANN、OPP、ATB、Python 和运行依赖也必须存在。此包把 Python 依赖安装与源码构建放进 `setup.sh`；系统层的驱动、固件、CANN 和 ATB 由目标服务器自行安装。

| 项目 | 已验证基线及目标要求 |
|---|---|
| 系统与 CPU | Linux aarch64；原机 Huawei Cloud EulerOS 2.0、Kunpeng-920、192 CPU 核 |
| NPU | 使用逻辑设备 0、1、2、3，共四卡；原机每卡约 32 GiB HBM，HCCL 通信正常 |
| 主机内存 | 原机约 755 GiB。CPU 专家需要数百 GiB 内存，建议同级容量；不能只按 NPU 显存评估 |
| 驱动/固件 | 与设备和 CANN 匹配；原机 `npu-smi` 显示 26.1.0，原始设备输出见依赖审计 JSON |
| CANN | 原机 `/usr/local/Ascend/cann-9.1.0`；需要 toolkit、运行库、对应 OPP 算子组件 |
| ATB | 原机 `/usr/local/Ascend/nnal/atb/9.1.0/atb/cxx_abi_1`，以 `--cxx_abi=1` 加载 |
| Python | Python 3.11，原机 3.11.18；需要 venv、pip 和开发头文件 |
| PyTorch | `torch==2.10.0+cpu`、`torch-npu==2.10.0.post4`，由脚本获取，不用 CUDA torch |
| Transformers | `5.5.4`，已固定 |
| 系统构建工具 | `gcc`、`g++`、`make`、`git`、`patch`；原机 GCC 10.3.1；CMake、Ninja、pybind11 等由脚本安装 |
| 磁盘/网络 | 权重另计，建议为环境、源码和编译预留至少 30 GiB NVMe；安装时能访问包源和构建依赖源 |
| 权限 | 账号能访问设备、驱动、权重，能写解压目录；系统组件安装由管理员完成 |

默认原生构建目标为 `ascend910b1`，与原插件的 A2 构建配置一致。它是构建参数，不表示通过改名就能让其他芯片兼容。设备类型不同时必须确认 CANN 支持、选择适合的 `--soc-version`，并重新验收；不承诺任意 x86/ARM 或任意昇腾卡都能直接运行。

## 权重目录

原机路径 `/mnt/nvme1n1/bf16/w8a8-mtp`，目标机可改为 `/data/models/w8a8-mtp`。需要同一套兼容的 DeepSeek-V4-Flash W8A8 safetensors 权重及 config/tokenizer 文件，CPU 加载器要求相应 INT8 weight、scale、offset 结构。

原机检查为 70 个分片、总计 300,013,759,966 字节，`model_type=deepseek_v4`、`architectures=["DeepseekV4ForCausalLM"]`。文件数只能作为完整性参照，不能证明来源一致。不要替换成旧 GGUF、任意其他量化版本或只有 BF16 基础权重的目录。

预检查会核对 config、索引声明的分片、tokenizer 和实际软件导入，不下载权重，也不对约 300 GB 权重逐字节重新求哈希。完整加载由四卡启动完成。

## 安装、启动和聊天

从本次 GitHub 分支获取服务如下。后文日常命令用 `/opt/ktv4-service` 作为示例目录；实际 clone 后的服务位于 `/opt/modorbit-delivery/ktv4-service`，请相应替换，也可以将服务文件夹放到 `/opt/ktv4-service`。脚本按自身位置定位。

```bash
git clone --branch codex/ktv4-service-20261110 \
  https://github.com/MODORBIT/modorbit.github.com.git /opt/modorbit-delivery
cd /opt/modorbit-delivery/ktv4-service

# 系统组件、Python 3.11 和模型已准备好后：
bash setup.sh --model-path /data/models/w8a8-mtp

# 安装通过后，自动启动四卡和 API，随后进入问答：
bash start.sh
```

路径或 Python 位置不同可以显式配置：

```bash
bash /opt/ktv4-service/setup.sh \
  --python /usr/bin/python3.11 \
  --model-path /data/models/w8a8-mtp \
  --cann-env /your/Ascend/ascend-toolkit/set_env.sh \
  --atb-env /your/Ascend/nnal/atb/set_env.sh \
  --soc-version ascend910b1
```

只查看安装计划、不创建环境、不改配置、不启动服务：

```bash
bash /opt/ktv4-service/setup.sh --plan --model-path /data/models/w8a8-mtp
```

`--plan` 仍检查系统、Python、关键路径和系统命令。安装脚本不自动获取驱动、CANN、ATB 或模型，也不修改它们。不会覆盖已有非 venv `env210`。`--skip-deps` 仅适用于本包 `env210` 中已经具备匹配依赖和构建工具的情况，仍会构建/安装本包服务库。

安装会创建 `env210/`、`cache/`、`run/` 和 `deployment.env`。配置保存权重路径、CANN/ATB 环境脚本；外部显式传入的同名环境变量优先。`config/runtime.json` 是原机证据，不是目标机启动配置。

普通包源由 `PIP_INDEX_URL` 控制；CPU PyTorch 默认从 `https://download.pytorch.org/whl/cpu` 获取，可用 `KTV4_TORCH_INDEX_URL` 指定兼容镜像。若所用镜像缺少指定版本/架构的 wheel，需先取得兼容包，不能随意升级 torch 或换成 CUDA 包。

`deploy/requirements.runtime.lock` 和 `deploy/requirements.build.lock` 是安装输入。根目录 `requirements.lock.txt` 是原机完整环境快照，含 CANN 自带组件和未使用扩展，不直接整体 pip 安装。安装用 `--no-deps` 保持原机实际工作组合，避免上游开发版对 torch 2.11 或 Triton 旧 numpy 约束覆盖已验证版本。原机缺失的可选后端/开发依赖在 `config/dependency_install_plan.json` 如实记录，不声称本包支持所有可选功能。

vLLM 以 `VLLM_TARGET_DEVICE=empty` 构建，实际计算走四个自定义 worker。vLLM-Ascend 以 `COMPILE_CUSTOM_KERNELS=1` 构建原生扩展和 ACLNN 自定义算子。包内无 `.git`，版本由安装脚本明确传入；仓库内已有第三方构建源码保留。不能用关闭算子编译来跳过需要的依赖。新机安装和编译时间取决于 CPU、CANN 和网络，不等于原机模型启动时间。

日常命令：

```bash
bash /opt/ktv4-service/start.sh --no-chat   # 只启动后台服务
bash /opt/ktv4-service/chat.sh              # 连接现有服务聊天
bash /opt/ktv4-service/chat.sh --prompt '你好'
bash /opt/ktv4-service/status.sh
bash /opt/ktv4-service/stop.sh
```

聊天内 `/clear` 清空对话，`/help` 查看帮助，`/exit` 退出。退出聊天保留后台服务。客户端不发送 `max_tokens` 或 `max_completion_tokens`，正常到 EOS，输入输出仍共享上下文容量。默认上下文 1,048,576 token，完整百万 token 推理未经验证；一次处理一个请求，MTP 关闭。`DEEPSEEK_MAX_SEQ_LEN` 可在启动前调整上下文配置。

首次需要加载约 300 GB 权重，原机最终测试约 118 秒就绪；首次未缓存输入形状可能编译数分钟，客户端每 15 秒显示等待。去掉输出上限不会消除输入形状引发的编译。

API 默认 `0.0.0.0:8000`，健康检查 `http://127.0.0.1:8000/health`，接口 `/v1/chat/completions`，模型名 `deepseek-v4-flash`。master 端口 31220，HCCL 端口范围 31000–31063/31100–31163，应避免冲突。

输出保存在 supervisor 有界内存缓冲；失败诊断写 `run/state.json`。少量驱动当前运行文件可能仍生成，启动/停止时清理旧日志。`stop.sh` 仅操作本项目记录的进程。

## 实际代码调用链

```text
start.sh
  ├─ app/service.py
  │   ├─ app/launch_workers.sh → 四个 app/worker.py
  │   │   ├─ app/legacy_reference.py → 模型构造/权重加载/兼容数学
  │   │   ├─ app/official_reference_model.py → 模型结构
  │   │   └─ app/runtime.py → CPU 专家及 NPU 计算
  │   └─ app/launch_api.sh → vLLM API、调度和 tokenizer
  │       └─ app/executor.py → 文件 RPC → 四个 worker
  └─ chat.sh → app/chat.py → HTTP 流式回答
```

每层 256 个路由专家的 INT8 权重及计算在 CPU，四进程各负责 64 个；gate、路由和共享专家在 NPU。Gate 在四卡完整复制，非切成四个 gate 分片。前三层 hash 路由，后续 TopK；CPU 部分结果回到 NPU 后通过 HCCL 归约。原机 tensor 设备证据在 `config/post_cleanup_verification.json`，目标机启动后见 `run/rank0.json` 至 `rank3.json`。

`vendor/` 还包含上游库其他模型和可选模块，它们并非都会在当前问答执行。当前主模型实现以 `app/` 为准，不应把 Ascend 库中的标准 `models/deepseek_v4.py` 当成当前自定义 worker 的主实现。

## 每个文件的作用和完整性

**`文件逐项说明.md` 为每个交付文件提供独立条目。** 主服务文件有具体职责说明；上游和第三方文件根据路径、模块说明、顶层类/函数生成可检索索引，区分服务计算、支持库、算子构建、第三方源码和生成描述，不把未调用代码称作当前执行路径。

`delivery_manifest.json` 提供每个文件的当前 SHA-256、原服务器绝对来源和是否为迁移新增/修改；`export_manifest.json` 保留原导出值。说明文件自身和校验清单也有索引条目；校验清单不计算自身的递归哈希。

## 新机器完成验收的标准

安装结束后 `config/target_preflight.json` 应为 `passed: true`。随后检查真实模型运行：

```bash
bash /opt/ktv4-service/start.sh --no-chat
bash /opt/ktv4-service/status.sh
bash /opt/ktv4-service/chat.sh --prompt 'What is 2 + 2? Give only the answer.'
bash /opt/ktv4-service/chat.sh
```

四个 rank 应就绪，`/health` 为 200，算术回答 `4`，再验证中文和多轮历史。状态为 `failed` 时查看 `run/state.json` 的 `error`/`last_output`，处理 ABI、CANN 编译、缺库或权重格式问题。只有目标机完成这一步，才算该机器实际部署成功。
